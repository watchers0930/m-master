# 04 Agent Structure

## 목적

`m-master` 개발 시 병렬 작업이 가능하도록 역할을 고정하고, 각 역할의 책임과 산출물을 명확히 나눈다.

## 기본 구조

- 메인 컨트롤
  - PM 겸 통합 책임
- 에이전트 1
  - 프로덕트 기획
- 에이전트 2
  - 디자인
- 에이전트 3
  - 프론트엔드
- 에이전트 4
  - 백엔드
- 에이전트 5
  - 검증

## 역할 정의

### 메인 컨트롤

- 전체 우선순위 결정
- 범위 조정
- 위키 기준 적용 여부 확인
- 에이전트 작업 분해
- 최종 통합과 승인

### 프로덕트 기획

- 사용자 흐름 정의
- 기능 명세 작성
- 예외 케이스 정리
- 문구와 상태 정의
- 기능 위키 초안 작성

### 디자인

- 정보구조와 화면 구성
- 상태별 UI 정의
- 공통 컴포넌트 패턴 정리
- 디자인 시안과 상호작용 기준 정리

### 프론트엔드

- 화면 구현
- 공통 컴포넌트화
- 상태 처리
- 사용자 입력 흐름 개선
- 디자인 시스템 반영

### 백엔드

- DB 모델
- API 설계
- 서비스 계층 구현
- AI 생성, 검수, 발행 흐름
- 로그와 작업 상태 관리

### 검증

- 규칙 문서 기준 체크
- 테스트 시나리오 작성
- 테스트 도메인 검증
- 배포 전 리스크 점검
- 위키 누락 항목 확인

## 소유 범위 원칙

- 같은 파일을 여러 에이전트가 동시에 수정하지 않는다.
- 기능 단위로 소유 범위를 나눈다.
- 설계 기준이 없는 구현은 먼저 기획 또는 위키가 선행한다.
- 프론트와 디자인은 공통 컴포넌트 기준을 공유한다.
- 백엔드는 기획 문서와 데이터 모델 합의 후 구현한다.

## 작업 순서

1. 메인 컨트롤이 범위를 자른다.
2. 기획이 흐름과 예외를 먼저 정리한다.
3. 디자인이 화면 구조와 컴포넌트 기준을 잡는다.
4. 백엔드와 프론트가 병렬 구현한다.
5. 검증이 중간부터 붙어서 문제를 조기에 발견한다.
6. 메인 컨트롤이 결과를 통합한다.

## 인수인계 규칙

- 모든 역할은 결과만 넘기지 말고 판단 기준을 같이 남긴다.
- 위키 문서 링크를 함께 남긴다.
- 추정이나 가정이 있으면 명시한다.
- 다음 역할이 바로 이어서 작업할 수 있게 입력과 출력이 보여야 한다.

## 금지

- 역할 경계 없는 무분별한 병렬 작업
- 같은 파일 동시 수정
- 위키 기록 없는 설계 변경
- 검증 없는 완료 선언
