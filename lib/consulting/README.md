# Consulting backend

`POST /api/consulting` creates one validated strategy per frozen input; completed input replays return 200, new results 201. `GET` reads a report or cursor-paginated history without generation or billing. Contracts live in `types/consulting.ts` and `schemas/consulting.ts`.

History returns `ConsultingReportSummaryDTO` using an explicit column projection: metadata, diagnosis summary and the bounded budget proposal (retained for the existing history budget badge). It never loads or parses `inputSnapshot` or `strategyJson`. Evidence and the full strategy remain available through the `reportId` detail query.

Source reads use a repeatable-read snapshot of the last thirty completed UTC days. A source SQL failure aborts that transaction; a bounded retry excludes the failing source and re-reads all survivors in a fresh consistent snapshot, rather than attempting to reuse an invalid Prisma connection. Old technical audits retain their actual observation timestamp and a stale warning. GEO uses the existing full-denominator SQL aggregate, including null rates. Keywords, rankings, competitor references and citation evidence are bounded; input bytes and output tokens are capped. Oversized evidence is deterministically shortened and selected by source (aggregate metrics first), with omissions recorded in limitations. Hashing and persistence use exactly the reduced prompt snapshot.

GA4 integration is deliberately incomplete: AnalyticsDaily and existing A/B snapshots do not establish property/host/collection-success provenance. The read-only adapter returns `unmapped` or `missing`, never manufactured observations or fallback zeros. Safe collection metadata and domain/property binding are a prerequisite to using GA4 metrics. It performs no network collection. The UI and generation gate explicitly support stored SEO/GEO only; GA4 visitor, page and traffic-source performance is excluded. Existing lib/ga4 clients use global credentials/property and cannot safely attribute tenant/domain performance.

Owner locks serialize GEO/SEO/consulting reservation checks. A short transaction claims the input and reserves a conservative token ceiling; no transaction spans the LLM request. SDK retries are disabled. Valid usage is settled once in a single transaction containing ledger insertion, report update, reservation release and audit event. Invalid strategies still record usage. Confirmed SDK pre-execution HTTP rejections (including authentication/permission/rate rejection) release the reserve atomically and record request_rejected. Network loss, timeout, missing usage and settlement failures retain their reservation and block automatic replay. If uncertainty persistence itself fails, the durable generating row/reservation still prevents replay. Operators must reconcile the attempt and ledger before releasing uncertain reserves; no automatic cost reconciliation or force-regeneration endpoint exists.

Consulting reads and generation lookups reconcile owner-scoped stale `generating` rows under the owner lock, in an independent transaction so a later budget denial cannot roll recovery back. The five-minute lease exceeds the route lifetime (90s) and SDK timeout (60s). Expired rows with `startedAt` become `uncertain` and retain reserves; expired rows without `startedAt` become `failed` and release reserves because the atomic start guard prevents a subsequent paid call. Both retain the input hash and emit one audit event (`consulting.stale_uncertain` or `consulting.expired_unstarted`) with report/attempt IDs. Only unstarted or confirmed rejected failures with zero reserve and no ledger may acquire a new attempt under the owner lock, atomically with budget re-reservation and a new durable reservation event. The stale worker is fenced by attemptId. Completed results remain idempotent and charged/uncertain attempts cannot replay. Active leases and other owners are untouched. A late response may still settle an uncertain attempt exactly once. Recovery runs on access, not a background timer. Operators must reconcile `consulting.stale_uncertain` against provider usage and the ledger before releasing its monetary hold; automatic expiry does not assume an unbilled request.

Frequency policy is optional: set both `CONSULTING_GENERATION_LIMIT` (positive integer) and `CONSULTING_GENERATION_WINDOW_SECONDS` (positive integer). Window counts use INSERT-only consulting.reserve audit events, including failed/rejected/retried/deleted reports. Every new attempt emits exactly one event in the reservation transaction. No commercial count is invented when policy is absent. Plan and monetary budget limits always apply. Domain deletion reconciles expired unstarted work, blocks active/uncertain reports and preserves the cost/audit ledger when completed history is removed.

Domain selection uses owner-scoped `/api/consulting/domains` server search and stable `(createdAt DESC, id ASC)` cursor pages. Cursors are bound to the owner and search; direct domain links resolve through an owner-filtered lookup, including domains beyond the first page.

The SQL migration validates table/index/FK structure and applies additively. Production application is outside this implementation scope. Never point tests at a real database. The DB test builds its own PostgreSQL instance using a separately installed `@electric-sql/pglite-socket` package:

```sh
npx tsc --noEmit --incremental false
PGLITE_SOCKET_PACKAGE=/path/to/node_modules/@electric-sql/pglite-socket node --test lib/visibility/__tests__/*.test.cjs lib/seo/__tests__/*.test.cjs lib/consulting/__tests__/*.test.cjs
NODE_PATH=/path/to/node_modules PGLITE_SOCKET_PACKAGE=/path/to/node_modules/@electric-sql/pglite-socket node --test lib/seo/__tests__/database.integration.cjs lib/visibility/__tests__/migration.integration.cjs
```

LLM responses are mocked in tests; no paid API is invoked. The isolated consulting DB suite covers drift and repeated migration, IDOR, concurrent generation, free replay, failed-output billing, timeout/missing usage, reservation interaction, transactional settlement rollback and deletion/cursor lifecycle. Frontend visual validation and production migrations are separate release steps. The pre-existing central Prisma schema exceeded 500 lines before this change (501); the additive model makes it 533. All new route/service/schema/type/test files stay below 500 lines. Splitting the central Prisma schema requires a separate CLI schema-path configuration change beyond this task's permitted paths.
